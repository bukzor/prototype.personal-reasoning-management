# host

How the ledger meets a proof engine: the encoding commitments (`HYP_FIAT`,
`HASH_FORMAL`, `NATIVE`) and the command surface they support. Names engine
parts, never a particular engine — that is `world`'s job.

- `prior:` purpose
- `ontology:` engine, kernel, elaborator, environment, declaration, proof term,
  syntax, import, substrate, translator, command, query
- `defeated by:` a host missing one of those parts — a checker with no
  elaborator, or an engine with no persistent environment

- HOST_DB: "Claim S has status P" is always encodable as further host declarations; the host environment is already a persistent claim database
- REFLECT_LIMIT <- HOST_DB: HOST_DB is sound for the ledger's own object language and false as a claim about the host's logic. No engine fully internalizes itself, so propositions *about the engine* — that its kernel is sound, what it accepts — are never ledger claims the way corpus claims are; they enter only as trust-base entries. This is the ceiling on how much the ledger can absorb, and it is a property of proof engines, not a gap in this design
- DELEGATE!: All proving is delegated to the host engine; the system never evaluates entailment -- authority: user
- ENC_CHOICE <- HOST_DB, DESIGN_FIAT: An unforced encoding choice selects which experiment runs; it must be explicit and recorded with an author
- FIAT_FORMS <- STIP: Stipulations admit two host encodings — global (environment-level fiat) and hypothetical (context-level: telescopes, sections, locales, frames). Hypothetical wins on two counts: TRUST_BASE becomes kernel-visible in the claim itself, and staleness becomes automatic — under global fiat a stipulation's dependency runs invisibly through the environment, so amending it changes no dependent's statement and no dependent's hash, and the ledger must track the consequence by hand. The global form is therefore given no route into the ledger at all: an escape hatch that exists gets used
- HYP_FIAT! <- FIAT_FORMS, HYP_CONTENT: Hypothetical fiat is the sole encoding for ledger-authored stipulations, all substrates; host-library global axioms are boundary conditions in TRUST_BASE, out of scope -- authority: user
- FIAT_SHIFT <- HYP_FIAT!, VERDICT: A ledger stipulation is never proven in the host, only assumable — provenness-by-fiat is a ledger status, not a host fact; recorded as a deliberate reinterpretation of "proven by fiat"
- FRAME_BUNDLE+ <- HYP_FIAT!: A host whose scoped-hypothesis mechanism does not compose across imports is the weak point for hypothetical fiat; there, each claim's hypotheses are bundled into a record — a frame — and threaded explicitly. Telescope management is the standing implementation cost of HYP_FIAT, and it lands on ledger machinery rather than on the authoring surface, which is what a command surface is for
- HASH_FORMAL <- HASH_ID: Hashing formal content is a per-substrate commitment, made here; ledger identity stays surface-only. The hashed object is the parsed-but-unelaborated form, since elaborated terms are version-unstable; cross-version stability is unsolvable at the term level, so toolchain bumps re-baseline and re-verify
- VERSION_OUT <- HASH_FORMAL, MONOTONE: The toolchain version is never an input to claim identity; it belongs to the verdict's authority. A host upgrade falsifies no recorded verdict — "kernel 4.12 accepted #a3f" stays true — so "re-verify" means acquiring a verdict under the new authority, not repairing a broken record. Where a bump does move the parsed form, that is an ordinary claim revision propagating ordinary staleness, not a versioning mechanism of its own
- TRUST_SWAP <- TRUST_BASE: Re-checking an exported proof drops the foreign kernel out of the trust base, replacing it with {re-checker + logic encoding + translator}; since that checker is small and the encodings are published, it is a strict trust improvement
- ALIGNMENT <- STIP, STALE_PROP: Cross-substrate statement alignment is hand-authored and permanent — one stipulation per concept per pair, forever, each with an author, revisable and staleness-propagating. It is the largest recurring cost in any multi-substrate design, and a single-substrate design deletes it outright
- NATIVE! <- DELEGATE!, HOST_DB, HASH_ID, META_DEPTH: The ledger is not bookkeeping beside the engine but objects inside it — claims are host declarations, and the registry is an object-language value the engine can quantify over; HOST_DB stops being an analogy and becomes the implementation. The rejected branch — registry as environment state, verbs writing into it — is queryable by metaprograms but not quantifiable as a term, so it caps every law below proof (META_DEPTH's defect) and parks the verdict machinery on the surface that churns. Available only in a self-hosting metalanguage -- authority: user
- EVIDENCE_SHAPE+ <- NATIVE!, SOURCE!, DEGREE!, PROJECTION: A claim's registry row carries its evidence whole: verdicts keyed by source and judged hash, each bearing degree and date — MONOTONE landed as data. Projections are engine functions over the row; none is ever a stored field
- INTROSPECT <- NATIVE!, EVIDENCE_SHAPE+: Status, trust base and staleness are computed from the registry value rather than maintained alongside it, so the ledger cannot drift from the proofs; TRUST_BASE and STALE_PROP get stronger under NATIVE, not weaker
- SELF_APPLY <- NATIVE!, REFLECT_LIMIT: What a self-hosting metalanguage buys beyond convenience: the ledger's own structures are object-language values, so claims *about the claim graph* are ordinary claims inside it. Graph properties — that every proof-depth claim carries a kernel verdict, that no stipulation is unauthored, that a claim's trust base is exactly its hypotheses — become theorems rather than scripts. REFLECT_LIMIT is the ceiling: the graph is reflectable, the engine is not
- LAW <- NATIVE!, META_DEPTH, CHECKER_COLLAPSE, SELF_APPLY, DELEGATE!: Laws are engine theorems about the registry value — the staleness scanner is the first — so law-checking is delegated to the kernel like any other proof, and SELF_APPLY's "theorems rather than scripts" is realized rather than aspired to. Laws are structural, never authority-adjudicating (ACCEPTED); REFLECT_LIMIT bounds them to the graph, never the engine
- TRUST_COST <- NATIVE!, TRUST_SWAP, CHECKER_COLLAPSE: NATIVE forfeits TRUST_SWAP, but CHECKER_COLLAPSE shrinks the debt: verdict machinery is definitions the kernel evaluates, not engine-internal code beside it. What stays outside the kernel is the translator and any law whose evaluation is delegated to compiled code — each a recorded, per-law trade
- AUDIT_SPOKE <- TRUST_COST, CHECKER: One backward-pointing spoke caps TRUST_COST: export the corpus and re-check it under an external kernel in CI, as an archival and audit channel rather than a workflow component
- UNTRUSTED_XLATE <- SURFACE_SPLIT, CHECKER_COLLAPSE, TRUST_BASE: The translator from authoring surface to registry is checker-shaped trust debt; it stays out of the trust base by having its output audited rather than its code trusted — round-trip, the registry printed back to surface form and diffed clean, is the decidable check, present from v1
- BASIS_API! <- NATIVE!, DESIGN_FIAT, SURFACE_SPLIT: The system's interface is a basis API: engine functions spanning the authoring operations — claim / describe / stipulate / assert is the current basis — plus the standing queries — status, staleness, trust base. Warranting is not an operation: it is what the kernel accepting a proof, or an authority tag on a stipulation, already does. Every user surface — CLI, LSP, editor — is a projection over the basis, none frozen: surfaces multiply and verbs get recut freely so long as the basis spans the workflow. Authoring lands as edits the translator ingests; queries are functions over the registry value -- authority: user
- VERB_TARGETS <- HYP_FIAT!, DEPTH_ATTEST, UNTRUSTED_XLATE: The translator's mapping: `claim` → registry row only (shallow); `describe` → a proposition-valued definition that elaborates, hash stored, no proof demanded; `stipulate` → a hypothesis-bundle frame, each field registered as an STIP claim with an authority; `assert` → a theorem over that frame, with dependency edges walked out of the proof term (proven)
- NO_AXIOMS <- CHECKER, VERDICT: Verdict-claims live in the ledger only, never as host axioms
- IMPORT_FITS <- NO_AXIOMS, VERDICT, CHECKER: A certification imported from another system is a verdict-claim already — authority = {foreign kernel + version, translator + version, alignment map, proving logic} — so foreign proofs never contaminate the host, and no new node type is needed to accept them
- FALLOUT! <- LAW, PROJECTION, INFER!: Revision opens an interval in which the corpus is not yet entirely consistent, and the system owes ergonomic affordances for the time and effort restoring consistency takes: the staleness query reports all of the debt, re-adjudication proceeds over days without taxing the daily loop, and an honest revision is never punished harder than silence. Acknowledgement-clears-red — a fresh verdict at the current hash, degree repriceable, one cheap act per dependent — is one candidate affordance, not the commitment; OBO's obsoletion-with-replaced-by pointers is prior art for another -- authority: user
- LAW_AUTHOR+ <- LAW, META_DEPTH, BASIS_API!: Authoring a law's proven rung means writing engine code — the one workflow off the markdown surface — and the trade is recorded as accepted: laws are rare, claims are daily. Per META_DEPTH the cost is per-rung, not per-law: a law is *stated* from the surface like any claim; only its proof is engine work
- V1_CHECKERS+ <- CHECKER, DELEGATE!, LAW, UNTRUSTED_XLATE: The first checker set = host kernel + the well-formedness law — unmanaged staleness debt a conjunct of well-formedness (FALLOUT!), evaluated by the staleness query, projectable to a CI check — plus the round-trip check; the trust-base query is an axiom-collection over the frame's fields. A first set, not a freeze: checkers accrue
- NO_SIDECAR <- NATIVE!: Persistence is ordinary declarations — the registry value is source, compiled into artifacts like any other definition, with no runtime state at all. The rejected branch, extension state riding beside the declarations, survived imports but was invisible to export tooling
